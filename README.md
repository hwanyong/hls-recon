# hls-recon

HLS 송출 데이터를 로컬 영상 파일로 재조립하고, **송출이 온전했는지 검증**한다.

> **사용 범위**
>
> 본인이 접근 권한을 가진 스트림에만 사용할 것. 이 도구는 송출 무결성 검증을 위한
> 것이며, 권한 없는 콘텐츠의 취득·재배포에 쓰는 것은 사용자 책임이다.
>
> DRM 은 다루지 않는다. Widevine·FairPlay·PlayReady·SAMPLE-AES 로 보호된 스트림은
> 코드 레벨에서 거부한다 (`playlist.py` — `KEYFORMAT=identity` 인 AES-128 만 처리).
> RFC 8216 §4.3.2.4 의 AES-128 은 평문 키를 URI 로 내려주는 링크 보호 수준이지 DRM 이
> 아니다.

## 왜 ffmpeg 한 줄로는 부족한가

```bash
ffmpeg -i master.m3u8 -c copy out.mp4     # 받아진다. 그러나 —
```

이 명령은 세그먼트가 HTTP 404 로 빠져도 **조용히 건너뛰고 exit 0 으로 끝난다.**
총 재생 길이도 그대로다 — MPEG-TS 세그먼트는 절대 표시 시각(PTS)을 품고 있어
중간 조각이 사라져도 뒤 조각의 시각이 원래대로 유지되기 때문이다.

실측한 사례 (본 저장소의 회귀 테스트):

```
6초 세그먼트 1개 결손 → ffmpeg 종료 코드 0, 출력 길이 30.03s (정상과 동일)
                     → 실제로는 5.99s ~ 12.02s 구간이 통째로 비어 있음
```

hls-recon 은 재조립 자체는 ffmpeg 에 위임하고, **ffmpeg 가 알려주지 않는 것만**
따로 계측한다: 세그먼트별 HTTP 결과와 지연, MPEG-TS 연속성 카운터, 재조립본의
타임라인 결손.

## 설치

```bash
# 요구사항: python 3.10+, ffmpeg/ffprobe (PATH 에 있어야 한다)
brew install ffmpeg

pip install .        # hls-recon 명령이 설치된다 (cryptography 는 함께 딸려온다)
```

설치하지 않고 저장소에서 바로 쓰려면 `./hls-recon` 이 실행 파일이다. 어디서나
쓰려면 심볼릭 링크를 건다.

```bash
pip install cryptography            # AES-128 스트림을 다룰 때 필요
ln -s "$PWD/hls-recon" /usr/local/bin/hls-recon
```

## 사용

```bash
# 구조만 조사 — 다운로드 없음
hls-recon https://cdn.example/master.m3u8 --probe-only

# 재조립 + 전체 검증
hls-recon https://cdn.example/master.m3u8 -o out.mp4 --report result.json

# 앞 20개 세그먼트만 빠르게 표본 검증
hls-recon https://cdn.example/master.m3u8 -o sample.mp4 --limit 20

# 화질 지정 (Referer 는 대개 자동으로 붙는다 — 아래 '접근이 막힌 스트림')
hls-recon https://cdn.example/master.m3u8 -o out.mp4 --height 1080 --referer https://site.example/

# 로그인이 필요한 스트림 — 브라우저 쿠키를 그대로 전달
hls-recon https://cdn.example/master.m3u8 -o out.mp4 --cookie 'sid=abc; token=xyz'

# 대용량: 계측 생략하고 빠르게 받기만
hls-recon https://cdn.example/master.m3u8 -o out.mkv --mode remux --no-decode-check
```

## 시리즈 — 목록 주소 하나로 전편

`-o` 에 **폴더**를 주고 시리즈 목록 페이지 주소를 넘기면 회차를 차례로 받는다.
회차 주소(1화 링크)를 줘도 그 시리즈의 목록으로 올라간 뒤 전편을 훑는다.

```bash
hls-recon 'https://site.example/c/작품제목' -o ~/Movies
hls-recon 'https://site.example/c/작품제목' -o ~/Movies --episodes 5-12 --container .mkv
hls-recon 'https://site.example/c/작품제목' --probe-only     # 회차 목록만 보기
```

이미 받아둔 회차는 건너뛴다(`--overwrite` 로 다시 받는다). 중간에 끊기면 만들다 만
파일을 지우고 끝낸다 — 남겨두면 다음 실행이 완성본으로 오인해 건너뛰기 때문이다.

### 다시 실행하면 빠진 회차만 받는다

같은 시리즈를 같은 폴더에 다시 걸면 폴더를 먼저 훑어 **없는 회차와 깨진 회차만**
받는다. 27화 중 3화가 비었다면 그 3화만 받는다.

```bash
hls-recon 'https://site.example/c/작품제목' -o ~/Movies     # 두 번째 실행 — 빠진 것만
hls-recon 'https://site.example/c/작품제목' -o ~/Movies --probe-only   # 뭐가 빠졌는지만 보기
```

```
  재고          : 25개 있음 '그렌라간', 손상 1개 — 받을 것 3개 (구조만 확인 — …)
```

세 가지를 판단에 넣는다.

| 무엇 | 왜 |
|---|---|
| **번호로 견준다** (파일명이 아니라) | 저장 이름은 플레이어가 정해서 재생 소스를 발급받아야 알 수 있다. 이름을 안 뒤에 건너뛰면 다 받아둔 27화에도 발급 요청이 80여 건 나간다. 회차 번호는 목록에 이미 있어 공짜다 |
| **확장자를 가리지 않는다** | `--container` 를 바꿔 실행하면 이름은 같고 확장자만 다르다. 완전 일치로 보면 전부 없는 것이 되어 다시 받는다. `그렌라간3.mp4` 와 `그렌라간03.mkv` 는 같은 3화다 |
| **온전한지까지 본다** | 강제 종료·전원 차단으로 남은 조각은 다음 실행에서 '이미 있다'로 읽혀 **그 회차가 영원히 복구되지 않는다** |

온전한지는 컨테이너 구조만 본다 — MP4 계열은 최상위 상자를 훑어 `moov` 가 있고
상자 경계가 파일 끝과 맞는지, MKV·TS 는 서명과 동기 바이트를 본다. 본문은 읽지
않으므로 파일이 커도 빠르다. 실제로 열리는지까지 보려면 `--verify-existing` 을
붙인다(ffprobe 로 회차마다 연다 — 느리다).

### 자막만 빠진 회차 — 영상 없이 자막만 메운다

영상은 멀쩡한데 자막만 없는 회차는 기본적으로 **다시 받지 않고 알리기만 한다.**
자막 하나 때문에 수백 MB 를 다시 받는 것은 대가가 맞지 않는다. 폴더의 절반 이상이
자막을 갖고 있을 때만 '빠졌다'고 본다 — 원래 자막이 없는 작품과 구별해야 한다.

`--refill-subs` 를 붙이면 그 회차의 **자막만** 받아 영상 옆에 놓는다.

```bash
hls-recon 'https://site.example/c/작품제목' -o ~/Movies --refill-subs
hls-recon 'https://site.example/c/작품제목' -o ~/Movies --refill-subs --sub-guess  # 선언이 없는 송출
```

자막은 영상과 다른 트랙(또는 아예 다른 파일)이라 따로 받을 수 있다. 회차의 재생
소스만 다시 발급받으면 자막 플레이리스트 주소를 알 수 있고, 세그먼트는 자막 것만
받으면 된다. 파일 이름은 이미 있는 영상을 따라가므로 재생기가 바로 짝을 짓는다.

영상 첫 세그먼트 **하나는** 받는다. `X-TIMESTAMP-MAP` 을 영상의 첫 표시 시각과
대조해야 자막이 제자리에 놓이기 때문이다 — 건너뛰면 받아지긴 해도 통째로 밀린
자막이 남는다. 받는 경로와 메우는 경로가 같은 추출 함수를 쓰므로, 나중에 메운
자막만 미묘하게 어긋나는 일이 없다.

`--flat` 으로 여러 작품을 한 폴더에 쌓아둔 경우, 번호만으로는 `A 03` 과 `B 03` 을
가를 수 없다. 파일명 줄기로 작품을 나눈 뒤 작품명과 맞는 무리를 고르고, 우열을
가리지 못하면 건너뛰기를 포기한다 — 잘못 짚어 회차가 조용히 빠지는 것보다 낫다.

### 왜 미리 모아두지 않는가

회차별 재생 주소는 **받기 직전에** 발급받는다. 두 가지 이유가 겹친다.

- 회차마다 CDN 경로가 불투명 해시라 1화 주소에서 2화를 유도할 수 없다.
- 발급된 주소에는 만료 시각이 박혀 있다(`…/master.m3u8?md5=…&expires=…`).

그래서 27화치 주소를 먼저 모아두고 순서대로 받는 방식은 뒤쪽 회차에서 반드시
만료로 깨진다. 목록만 먼저 확보하고 재생 주소는 그때그때 푼다.

### 페이지를 타고 들어갈 때의 Referer

각 단계는 서로 다른 곳에서 열린다 — 회차 페이지는 사이트 안에서, 플레이어는
회차 페이지의 iframe 으로, 재생 주소는 플레이어 안의 XHR 로. 브라우저가 보내는
것과 같은 Referer 를 단계마다 실어 보낸다. 하나라도 비면 서버가 **404** 로
돌려보내는데, 없는 페이지처럼 보여서 원인을 짚기 어렵다.

## 보관 구조

받은 파일은 시리즈 폴더에 넣는다. 파일명 끝의 화수를 떼어 시리즈를 가르며,
시리즈 모드에서는 사이트가 알려준 작품명을 폴더 이름으로 쓴다.

```
~/Movies/
  천원돌파 그렌라간/
    그렌라간01.mp4
    그렌라간01.srt
    그렌라간02.mp4
```

화수가 없는 이름(영화 한 편)은 폴더로 감싸지 않는다. `--flat` 으로 이 동작 전체를
끌 수 있다.

이미 흩어져 있는 파일은 `--tidy` 로 되모은다. 기본은 미리보기이고 `--apply` 를
붙여야 실제로 옮긴다. **같은 시리즈로 묶이는 회차가 둘 이상**인 영상만 대상이다 —
혼자뿐인 회차나 영화까지 넣으면 파일 하나짜리 폴더만 늘어난다. 자막 등 곁파일은
영상을 따라간다. 이름이 겹치면 덮어쓰지 않고 건너뛴다.

```bash
hls-recon --tidy ~/Movies/torrent
hls-recon --tidy ~/Movies/torrent --apply
```

## 접근이 막힌 스트림

### Referer — 대개 자동으로 붙는다

핫링크를 차단하는 CDN 은 플레이어 페이지의 origin 을
`Access-Control-Allow-Origin` 응답 헤더로 되돌려준다. **차단당한 403 응답에도
붙어 온다.** 그래서 첫 요청이 막히면 그 헤더를 읽어 `Referer`/`Origin` 을 스스로
채택하고 한 번 더 시도한다.

```
  source: https://cdn.example/master.m3u8
  Referer 자동 : https://site.example/ (서버가 알려준 허용 origin)
```

이 줄이 뜨면 별도 조치가 필요 없다. `--referer` 를 직접 주면 자동 채택은 하지 않는다 —
사용자 지정이 항상 우선한다.

자동으로 안 되는 경우는 서버가 `Access-Control-Allow-Origin` 을 아예 안 주거나 `*` 로
줄 때다. `*` 는 "아무 origin 이나 허용"이라 근거가 되지 못한다. 이때는 직접 지정한다.

```bash
hls-recon URL -o out.mp4 --referer https://site.example/
```

> ACAO 는 규격상 "브라우저 JS 가 응답을 읽어도 되는 origin"이지 "서버가 요구하는
> Referer"가 아니다. 둘이 일치하는 경우가 많다는 경험칙에 기댄 추정이므로, 어긋나면
> `--referer` 로 덮어쓰면 된다.

### 쿠키 — 직접 붙여넣는다

토큰 URL만으로 열리지 않고 세션 쿠키를 요구하는 CDN 이 있다. 브라우저 개발자도구
Network 탭에서 `.m3u8` 요청을 찾아 **Request Headers 의 `Cookie` 값을 그대로 복사**해
`--cookie` 에 붙여넣는다.

```bash
hls-recon URL -o out.mp4 --cookie 'sid=abc; token=xyz'
hls-recon URL -o out.mp4 --cookie 'Cookie: sid=abc; token=xyz'   # 접두어가 붙어 있어도 된다
```

값은 파싱하지 않고 통째로 `Cookie` 헤더에 실어 보낸다 — 이름/값으로 쪼갠 뒤 다시
조립하면 특수문자가 든 쿠키가 훼손되기 때문이다. 앞뒤 따옴표, `Cookie:` 접두어,
여러 줄로 붙여넣은 경우의 줄바꿈만 정리한다.

### 헤더는 어디로 가는가

요청 헤더의 출처는 한 곳(`Fetcher.headers`)이고, 네 경로가 모두 그것을 쓴다:
`segments` 모드의 세그먼트 수신, `remux` 모드의 ffmpeg, ffprobe 실측, 자막 트랙 추출.
브라우저 User-Agent 와 자동 채택한 Referer 도 여기 들어가므로 ffmpeg 쪽만 다른 조건으로
요청하는 일이 없다.

`--header 'K: V'` 로 임의 헤더를 더 붙일 수 있고, `--cookie` 와 `--referer` 는 각각
그중 `Cookie` / `Referer` 를 덮어쓴다.

> 셸 히스토리와 `ps` 출력에는 쿠키가 그대로 남는다. 공용 장비에서는 명령 앞에 공백을
> 넣어 히스토리 기록을 피할 것. `--report` JSON 에 남는 먹싱 명령에서는
> `Cookie`·`Authorization` 계열 헤더가 `***` 로 가려진다.

### 세그먼트가 `.html` 등으로 위장된 경우

확장자 기반 차단을 피하려고 세그먼트를 `1080p_010.html` 처럼 내보내고
`Content-Type: text/html` 로 응답하는 CDN 이 있다. 그대로 처리한다.

- 페이로드 판별은 헤더가 아니라 **선두 바이트**로 한다. `text/html` 이라고 선언된
  정상 세그먼트를 오류 페이지로 오인하지 않고, 반대로 토큰 만료 시 오는 진짜 HTML
  오류 페이지는 잡아낸다 — 이 CDN 에서는 둘의 헤더가 완전히 같아서 이 방식이 아니면
  구분할 수 없다.
- ffmpeg 은 확장자만 보고 세그먼트를 차단하는 기본값이 있어 `-allowed_extensions ALL`
  을 항상 넘긴다. 이 차단은 로컬 경로 세그먼트에만 걸리므로 원격 스트림은 원래
  영향이 없지만, 받아둔 세그먼트를 로컬 플레이리스트로 다시 검증할 때 필요하다.

## 자막

마스터 플레이리스트의 `#EXT-X-MEDIA:TYPE=SUBTITLES` 트랙을 함께 내려받는다.
기본값은 `--subs default` — `DEFAULT=YES` 또는 `AUTOSELECT=YES` 인 트랙만 받는다.

```bash
hls-recon URL -o out.mp4                        # 기본 트랙을 out.ko.vtt 등으로
hls-recon URL -o out.mp4 --subs all             # 전부
hls-recon URL -o out.mp4 --subs ko,en           # 언어 지정 (ko 는 ko-KR 도 매칭)
hls-recon URL -o out.mp4 --subs none            # 받지 않음
hls-recon URL -o out.mp4 --sub-format srt       # SubRip 으로 변환
hls-recon URL -o out.mkv --sub-embed            # 별도 파일 대신 컨테이너에 내장
```

`--sub-embed` 는 언어·제목 메타데이터와 forced 플래그까지 함께 넣는다.
`.mkv` 는 `subrip`, `.mp4` 는 `mov_text` 로 자동 변환된다.

`TYPE=CLOSED-CAPTIONS`(CEA-608/708)는 영상 스트림에 실려 오므로 별도 파일로 뽑을 수
없다. 선언된 트랙 목록만 리포트에 표시한다.

### 플레이리스트에 자막 선언이 없을 때 (sidecar)

자막을 `#EXT-X-MEDIA` 로 선언하지 않고 정적 파일로 따로 두는 송출이 있다. 트랙
목록에 나타나지 않으니 `--subs` 로는 잡히지 않는다. 이때는 URL 을 조립해 받는다.

```bash
hls-recon URL -o 그렌라간01.mp4 --sub-guess              # 출력 파일명으로 조립
hls-recon URL -o out.mp4 --sub-guess --sub-name 그렌라간01 # 이름을 따로 줄 때
hls-recon URL -o out.mp4 --sub-url https://cdn/a.srt      # 조립 없이 직접 지정
hls-recon URL -o 그렌라간01.mp4 --sub-guess --sub-range 01-27  # 이웃 화수까지
```

URL 세 조각의 출처가 각각 다르다.

| 조각 | 어디서 오는가 |
|---|---|
| 호스트 | **영상 응답이 알려준다.** 핫링크 차단 CDN 이 되돌려주는 `Access-Control-Allow-Origin` 이 플레이어 origin 이고 자막도 거기 있다. 이미 Referer 로 채택해 둔 값을 재사용하므로 추가 요청이 없다 (`--sub-origin` 으로 덮어쓴다) |
| 경로·확장자 | 사이트별 고정 규칙. `subtitles.SIDECAR_PATHS` 에 실측한 것만 둔다 |
| 이름 | **어디에서도 유도되지 않는다.** 영상 URL 이 불투명 해시라면 더욱 그렇다. 다만 받는 쪽은 이미 그 영상의 이름을 알고 있다 — 그래서 `-o` 의 파일명을 기본값으로 쓴다 |

이름은 화수 표기가 어긋나기 쉬워(`그렌라간1` vs `그렌라간01`) 후보를 만들어 존재하는
것을 채택한다. 자릿수 변형은 1~2자리에만 건다 — 3자리는 화수가 아니라 연도(`… 2026`)일
수 있고, 그것을 건드리면 원본과 무관한 이름이 만들어진다.

받은 파일은 **바이트 그대로 저장한다.** 중복 정리·정렬 보정은 조각을 이어붙인 산물에서만
생기는 문제라 완성 파일에는 걸지 않는다. 같은 URL 을 손으로 받은 결과와 대조할 수 있어야
하기 때문이다. 형식 변환은 `--sub-format` 이 원본과 다를 때만 한다.

응답이 자막인지는 **선두 내용**으로 판정한다. 자막을 `application/octet-stream` 으로 주는
서버가 있고, 반대로 200 으로 오는 HTML 오류 페이지도 같은 헤더를 달고 온다. 큐 타임코드가
하나라도 있는지가 유일하게 확실한 근거다.

### 자막에서 실제로 조정하는 것

자막도 영상처럼 조각나 있어서 이어붙이는 것만으로는 온전한 파일이 되지 않는다.
셋 다 실측으로 확인한 문제다.

| 문제 | 그대로 두면 | 처리 |
|---|---|---|
| 경계에 걸친 큐가 양쪽 조각에 실림 (규격이 허용) | 같은 자막이 두 번 — 6큐가 9큐로 | 시각·본문이 같은 큐를 제거 |
| 조각마다 붙는 `WEBVTT` / `X-TIMESTAMP-MAP` 헤더 | 그 문자열이 자막으로 화면에 표시됨 | 큐 본문에서 걷어냄 |
| `X-TIMESTAMP-MAP` 정렬 | 자막 전체가 일정량 밀림 | 영상 첫 표시 시각과 대조해 보정 |

마지막 항목이 특히 중요하다. `X-TIMESTAMP-MAP=LOCAL:...,MPEGTS:...` 은 자막 시각과
영상의 90kHz 클럭을 잇는 대응표인데, **ffmpeg 는 자막 플레이리스트를 단독 입력으로
열 때 이 매핑을 적용하지 않는다** — 정렬 기준이 될 영상이 그 입력에 없기 때문이다.
그래서 오프셋을 직접 계산해 sidecar 는 추출 후 큐를 이동시키고, 내장 모드는
`-itsoffset` 으로 넘긴다. 보정량은 리포트에 남는다.

### 두 가지 모드

| 모드 | 동작 | 쓸 곳 |
|---|---|---|
| `segments` | 세그먼트를 개별 수신하며 계측 → 로컬 병합 | **송출 검증**. 세그먼트별 지연·유실·중복까지 본다 |
| `remux` | 플레이리스트 URL 을 ffmpeg 에 직접 위임 | 빠르고 견고. LIVE·SAMPLE-AES 처럼 계측이 불가능한 경우 |
| `auto` (기본) | LIVE 이거나 세그먼트 단위 복호화가 불가능하면 `remux`, 아니면 `segments` | 대부분 이대로 두면 된다 |

두 모드 모두 재조립은 무손실이다 (`-c copy` — 재인코딩 없음).

## 검증 항목

| 항목 | 무엇을 잡나 | 판정 |
|---|---|---|
| 플레이리스트 | 세그먼트 수, 선언 길이, 암호화, 컨테이너 | 정보 |
| 세그먼트 수신 | HTTP 실패(토큰 만료·핫링크 차단), 재시도 발생 | 실패 → FAIL / 재시도 → WARN |
| 응답 지연 | TTFB p50·p95, 처리량 중앙값 | p95 > 3s → WARN |
| **페이로드 유효성** | **200 응답이지만 내용이 미디어가 아닌 경우** (오류 페이지) | 검출 → FAIL |
| 세그먼트 고유성 | SHA-256 중복 = 같은 조각 반복 송출 | 중복 → WARN |
| TS 무결성 | continuity counter 점프(패킷 유실), TEI, 동기 이탈, 미복호 패킷 | 동기 이탈·미복호 → FAIL |
| 길이 정합 | 실측 길이 vs EXTINF 선언 합계 | 한 세그먼트 이상 어긋남 → FAIL |
| **타임라인 연속성** | **재조립본의 결손 구간** — 총 길이가 맞아도 중간이 빈 경우 | 결손 → FAIL |
| 자막 추출 / 내장 | 트랙별 추출 성공, 큐 개수, 중복·헤더 정제량, 정렬 보정량 | 실패 → FAIL |
| 자막 타임라인 | 자막 시각이 영상 범위 안에 있는가 | 벗어남 → FAIL |
| 자막 일괄 수집 | `--sub-range` 로 함께 받은 이웃 화수 확보율 | 전멸 → WARN |
| 전체 디코드 | 끝까지 디코드되는가 (열리는 것과 다른 문제) | 오류 → FAIL |

종료 코드: `0` = PASS/WARN, `2` = FAIL. CI 파이프라인에 그대로 물릴 수 있다.

## 검증 항목이 실제로 동작하는가

검증 도구가 PASS 만 낸다면 아무것도 검증하지 못하는 것과 같다. 그래서 회귀 테스트는
"정상을 통과시키는가"와 함께 **"결함을 실제로 잡는가"**를 고정한다.

`tests/run.sh` 는 로컬에 HLS 스트림을 생성한 뒤(평문 TS / AES-128 / fMP4 /
멀티 variant / 자막 트랙) 결함을 주입해 검출을 확인하고, 마지막으로 같은 스트림에
대해 ffmpeg 단독은 조용히 성공한다는 사실까지 대조군으로 고정한다.

```bash
./tests/run.sh        # 통과 62 / 실패 0
```

| 주입 결함 | 잡아야 할 검사 |
|---|---|
| TS 패킷 12개 제거 | TS 무결성 (continuity counter 점프) |
| 세그먼트 중복 송출 | 세그먼트 고유성 (SHA-256) |
| 세그먼트 404 | 세그먼트 수신 + 타임라인 연속성 |
| 200 응답에 HTML 오류 페이지 | 페이로드 유효성 |
| 자막 `X-TIMESTAMP-MAP` 60초 어긋남 | 자막 타임라인 (별도 파일·내장 양쪽) |
| 자막 URL 이 200 으로 HTML 을 반환 | sidecar 수신 (선두 내용 판정) |
| 60%에서 잘린 MP4 · 0바이트 파일 | 재고 조사 (완성본으로 오인하지 않는가) |
| 자막만 없는 회차 | 자막 메우기 (영상을 건드리지 않고 자막만 놓는가) |

재고 조사는 **양방향으로** 고정한다. 너무 관대하면 깨진 파일이 완성본 행세를 해
회차가 영원히 빠지고, 너무 엄격하면 멀쩡한 27화를 매번 다시 받는다. 그래서 결함을
잡는 항목과 함께 정상 파일(`moov` 앞·뒤 양쪽 배치)을 온전하다고 보는지, 화수 표기와
확장자가 달라도 같은 회차로 읽는지를 같이 둔다.

`200 응답에 HTML` 항목은 헤더를 믿으면 놓친다. 테스트에서 서버는
`Content-Type: video/mp2t` 로 응답하지만 본문은 `<!DOCTYPE html>` 이다 — 그래서
헤더가 아니라 선두 바이트로 판정한다.

자막 결함은 sidecar 와 내장을 **따로** 고정한다. 자막을 컨테이너에 내장하면 전체
duration 이 자막 끝까지 늘어나므로, 기준선을 실측 길이로 잡으면 밀린 자막이 스스로
기준을 끌고 가 검사가 항상 통과해 버린다. 그래서 기준선은 플레이리스트 선언 길이다.

## 구조

```
hlsrecon/
  playlist.py   M3U8 파싱 — 마스터/미디어, EXT-X-MEDIA/KEY/MAP/BYTERANGE/DISCONTINUITY
  fetch.py      계측형 HTTP — 요청별 TTFB·처리량·재시도·SHA-256, URL 정규화
  series.py     시리즈 페이지 해석 — 회차 목록 발견 + 회차별 재생 주소 late resolution
  naming.py     이름 규칙 — 화수 표기·시리즈명의 단일 출처
  library.py    보관 구조 — 시리즈 폴더 배치, 흩어진 파일 되모으기
  inventory.py  재고 조사 — 이미 받은 회차 식별, 끊긴 파일 검출 (재실행 시 빠진 것만)
  decrypt.py    AES-128-CBC 세그먼트 복호화 (IV 기본값 = media sequence)
  tsanalyze.py  세그먼트 페이로드 판별 + MPEG-TS continuity counter 유실 검출
  subtitles.py  자막 트랙 선택·추출·정렬 보정·중복 정리
  probe.py      ffprobe 실측 — 스트림 정보, 타임라인 갭 스캔, 전체 디코드
  assemble.py   ffmpeg 위임 — 재조립·먹싱 (재인코딩 없음)
  report.py     계측치 → 판정 → 콘솔/JSON 리포트
  cli.py        진입점
```

## 알려진 한계

- **SAMPLE-AES / DRM**: 프레임 단위 부분 암호화나 Widevine·FairPlay 로 보호된
  스트림은 대상이 아니다. `auto` 모드가 `remux` 로 내리지만 ffmpeg 도 복호화하지
  못하므로 실패한다.
- **LIVE**: ENDLIST 없는 플레이리스트는 스냅샷 시점까지만 처리한다.
  세그먼트 단위 계측은 하지 않는다.
- **중첩 마스터**: variant URL 이 다시 마스터인 구조는 지원하지 않는다.
- **자막**: `TYPE=CLOSED-CAPTIONS`(CEA-608/708)는 영상에 실려 있어 별도 추출이
  불가능하다. 다국어 오디오(`TYPE=AUDIO`)는 목록에 표시만 하고 받지 않는다 —
  기본 오디오는 영상 variant 안에 들어 있다.
- **sidecar 자막의 이름**: 조립에 필요한 세 조각 중 이름만은 영상 쪽에서 유도할 수
  없다. 영상 URL 이 불투명 해시인 송출에서는 해시에서 이름을 역산할 방법이 없고,
  플레이리스트에도 제목이 없다. `-o` 의 파일명을 기본값으로 쓰되 어긋나면
  `--sub-name`, 규칙 자체가 다르면 `--sub-url` 로 넘어간다.
- **sidecar 자막의 정렬**: `X-TIMESTAMP-MAP` 이 없어 영상과의 오프셋을 계산할 근거가
  없다. 받은 시각을 그대로 믿고, 영상 범위를 벗어나는지만 사후 확인한다.
- **타임라인 갭 임계**: 프레임 간격 중앙값의 3배 또는 0.4초 중 큰 값. 가변 프레임률
  소스에서는 오탐이 날 수 있다 — `--no-gap-scan` 으로 끈다.
- **시리즈 해석은 사이트별 규칙**: `series.py` 는 실측한 한 사이트의 구조(회차 목록
  마크업, 플레이어 iframe, 재생 주소 발급 XHR)에 맞춰져 있다. 사이트가 구조를 바꾸면
  그 모듈만 고치면 되지만, 다른 사이트가 저절로 되지는 않는다.
- **재고 조사의 온전함 판정**: 기본은 컨테이너 구조만 본다. 상자 경계가 맞고 `moov`
  가 있으면 온전하다고 보므로, 구조는 온전한데 내용이 깨진 파일(중간 세그먼트가
  통째로 빠진 경우 등)은 걸러내지 못한다. `--verify-existing` 이 ffprobe 로 열어
  보지만 그것도 '열린다'까지이고 타임라인 결손은 보지 않는다 — 그 검사는 받는
  시점에만 한다.
- **재고 조사의 작품 식별**: `--flat` 으로 여러 작품이 섞인 폴더에서는 파일명
  줄기로 작품을 가른다. 작품명과 줄기의 우열을 가리지 못하면 건너뛰기를 포기하고
  파일명 완전 일치로 물러선다 — 안전한 쪽이지만 그만큼 재생 소스 발급 요청이 나간다.
- **화수 표기**: 이름 끝의 `01` · `1화` · `500회` 만 화수로 읽는다. 앞이 또 숫자면
  화수가 아니라 하나의 수로 본다(`Sky.Blue.2003` 은 영화이지 3화가 아니다).
  `S01E05` 꼴은 아직 읽지 않는다.

## 교재

이 저장소의 코드를 교재 삼아 **웹 스트리밍을 로컬 파일로 되돌리는 과정에 필요한
컴퓨터 과학 지식과 그 과정에 내재한 보안 한계**를 다룬 문서가 `docs/` 에 있다.
8부 39장 + 부록 4편.

```
docs/README.md          목차와 읽는 순서
docs/00-curriculum.md   지식 추출 매트릭스 — 코드 앵커 ↔ CS 개념 ↔ 보안 함의
```

모든 주장에 `file.py:line` 형식의 코드 앵커가 붙어 있고, 그 앵커가 실제 파일의 실제
줄 범위를 가리키는지는 기계적으로 검증된다.

```bash
python3 tools/check_docs.py docs         # 코드 앵커·상호 참조·구조·표기
python3 tools/check_svg.py docs/images   # 도식 렌더·테마 대응·접근성
```
